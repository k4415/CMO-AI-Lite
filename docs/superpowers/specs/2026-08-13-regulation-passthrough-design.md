# 表現レギュレーション パススルー化 修正計画書（Phase 1）

作成日: 2026-08-13
ブランチ: `feature/banner-image-prompt-writer` の続き（配色は同じプロンプト組み立て層の話のため分岐しない）
ステータス: 提案（レビュー待ち）
関連: `2026-08-12-banner-image-prompt-writer-design.md`

## 1. 背景

「青地に濃色文字で読めない」というバナー品質の報告から調査したところ、**配色事故そのものより深い問題**が見つかった。表現レギュレーションが機械的な文字列処理を何段も経る過程で、**意味が反転・欠落したままAIへ渡っていた**。

### 発見1: 文字色と背景色が同一色になっていた

確定パレットが `main #041024`（文字）/ `background #041024`（背景）と**同じ色**で、コントラスト比 1.00:1。全案件102枚中60枚（59%）が該当し、すべてcmo-ai-lite案件に集中していた。

画像モデルはこの実行不能な指示を回避するため独自に配色を作り、accent青（#2460F0）の面に main（#041024）の文字を置いた。これが「青地に黒字」の正体（3.63:1）。

原因は `extractPaletteFromText`（`src/core/banner-color-decision.js`）のフォールバック分岐。

```js
if (!roles.length) return colors.length === 1 ? { main: colors[0].color } : {};
```

ブランドカラー表の行「`| CMO Deep Navy | #041024 | 深みを出す締め色 | フッター、資料表紙、強調エリア |`」は役割キーワード（メイン／サブ／アクセント／背景）を含まず色が1つだけのため、この分岐が発動し**「限定使用の締め色」が文字色として採用**されていた。

同時に、正しい指定は両方とも失われていた。

- `#041024 背景 + 白文字 + #2460F0 アクセント` → 「白文字」の白がHEXでないため文字色が取れず `{background, accent}` のみ
- `| CMO Navy | #004AAD | ブランドの基調色 | ロゴ文字、見出し、本文強調 |` → 色と役割語の距離が40字制限を超え、何も抽出されない

### 発見2: 禁止事項が推奨事項として扱われていた

レギュレーションは元々Markdown文書だが、**行単位のフラットな配列**として取り込まれており、見出しと項目の親子関係が失われている。保存順で見ると構造は残っている。

```
16 | 組み合わせOK:
17 | #FFFFFF + #004AAD + #2460F0
...
21 | 組み合わせNG:
22 | #088C84 を全面背景にして、CMO AI本体のブルー感を消す。
23 | #FF6B3D をCTAや見出しの主役色として常用する。
24 | 赤、黄色、金、黒を大面積で組み合わせる。
25 | グラデーションを多用してロゴより派手にする。
```

しかし各行は独立したルールとして扱われるため、**「組み合わせNG:」配下の項目が「やるべき指示」（specifiedRules）としてAIへ渡っている**。実際に最終画像プロンプトへ「グラデーション」の文字列が入っていることを確認した。さらに23行目からはパーサが `accent: #FF6B3D` を抽出しており、**禁止色がアクセント色として採用**されていた。

### 発見3: NG判定が "Orange" の "ng" で誤爆していた

`classifyExpressionRules`（`src/core/banner-ai.js:1155`）の分類は文字列包含判定のみ。

```js
if (haystack.includes("ng") || haystack.includes("禁止") || haystack.includes("avoid")) ngRules.push(rule);
```

NG判定された6件のうち5件は、`Orange` に含まれる **"ora-ng-e" の ng** による誤爆だった。特に配色比率の指示が3行とも巻き添えで消えている。

```
CMO AI Lite: White・Cloud Gray 55-65%、Navy 20-25%、Blue 15-20%、Greenは原則使わない
```

これらは `pattern` が空のため置換処理でも何もしない。**NGとしても機能せず、指示としても届かない死んだ状態**。元のバナーが青と濃紺ばかりで白がほとんど無かったのは、この比率指示が消えていたことも一因と考えられる。

### 各工程に実際に届いていたもの（実測）

| 工程 | 届くもの |
|---|---|
| Stage 1 コピー開発 | specifiedRules（21件）の自然文 |
| Stage 2 promptJson | specifiedRules（21件、最大40件） |
| Stage 2b ライター | **届かない**（引数に `expressionRules` が無い。色は `colorDecision` のHEX4色のみ） |
| Stage 3 画像プロンプト | 生ルールは入らない。色は `colorScheme` のHEX4色に圧縮 |

最終プロンプトに `Cloud Gray` `55-65` `Signal Orange` は含まれず、`#041024` だけが残っていた。**色に関しては「27件の自然文 → パーサで4つのHEXに圧縮 → HEXだけ」**という経路で、人間が書いた文章はどこにも届いていない。

## 2. 設計方針

### 本質は「間違った断定を厳守させたこと」

壊れたのは、パーサが「#041024 は文字色だ」と**誤って断定**し、その断定を「厳守せよ」としてプロンプトへ入れたため。コントラスト計算や閾値による自動補正は、**間違った断定を後から補正する装置**にすぎない。断定をやめれば補正装置も不要になる。

### 採る方針: 色は「境界」として渡し、役割はAIが決める

コードが持つのは「使ってよい色のリスト」だけにする。役割（どれが文字でどれが面か）は指定せず、レギュレーション原文を**順序を保ったまま**AIへ渡す。Stage 2bのOpus 5ライターが判断して散文に書き下ろし、画像モデルがそれに従う。人間のデザイナーにブランドガイドを渡すのと同じ形。

原文を順序どおり渡せば、「組み合わせNG:」という見出しとその配下の関係もAIが読み取れる。**発見2は機械的な階層復元をせずに解決する**。

### この方針で不要になるもの

| 不要になるもの | 理由 |
|---|---|
| コントラスト閾値の設定 | 判断がAI側に移る |
| WCAG計算ロジック | 同上 |
| 案件ごとのレギュレーション点検作業 | 役割を誤読しても色群は変わらないため無害化 |

最後の行が実運用では最も大きい。今回はレギュレーションを人が書き換えて止血したが、この方式なら `main` が壊れていても事故にならない。「人が正しく書かないと壊れる」設計から「間違って書いても壊れない」設計への移行。

### 検討したが採らなかった案

| 案 | 不採用の理由 |
|---|---|
| 面と文字のペア構造（surfaces方式） | 設計として最も正しく拡張性もあるが、パレット構造の作り替えでカラー契約・テンプレ色中立化・既存データ互換に波及する。将来の移行先として温存 |
| コントラスト閾値で文字色を自動導出 | 閾値というチューニング項目が残り、運用で覚えることが増える。「必要な色だけ決めてAIに任せる」という方針に反する |
| 生成後に画像解析して低コントラストを検出しリトライ | 事後検証は複雑でリトライにより画像コストが倍。既存のOCR検証が機能不全である事実からも、事前確定のほうが確実 |
| 色に関する行だけを抽出してライターへ渡す | 抽出はまさに今壊れているアプローチ。キーワードで絞れば "Orange" 問題を別の形で再発させる。配色比率のような色名だけでは拾えない指示も落ちる |

## 3. 変更内容

**データ構造・パレット決定ロジック・カラー契約検証には触れない。** 変更するのは「AIへの渡し方」だけ。`promptJson.colorScheme` は従来どおり保存され、`assertBannerImageColorContract` の一致検証もそのまま通る。

### A. NG判定の誤爆を修正（`src/core/banner-ai.js`）

`classifyExpressionRules` の判定を単語境界マッチにする。

```js
// 変更前: "Orange" の ng で誤爆する
if (haystack.includes("ng") || haystack.includes("禁止") || haystack.includes("avoid"))

// 変更後: 独立した語としての NG のみを見る
if (/(^|[^a-z])ng([^a-z]|$)/i.test(haystack) || haystack.includes("禁止") || haystack.includes("avoid"))
```

検証済みの挙動:

| 入力 | 現行 | 修正後 |
|---|---|---|
| `成果保証や煽りコピーにOrange/Redを使う。` | NG | 指示 |
| `組み合わせNG:` | NG | NG |
| `\| Signal Orange \| #FF6B3D \| …` | NG | 指示 |
| `CMO AI Lite: White・Cloud Gray 55-65%…` | 指示 | 指示 |
| `グラデーションを使用禁止` | NG | NG |
| `avoid using red` | NG | NG |

全案件で `pattern` が空のため、この変更で置換処理の挙動は変わらない。分類が変わるのは5件で、うち3件が配色比率、1件がブランド色表の行、1件がNGリスト項目（下記リスク参照）。

### B. ライターへレギュレーション全文を渡す（`src/core/banner-image-prompt-writer.js`）

`writeBannerImagePrompt` に `expressionRules` 引数を追加し、**分類せず・並べ替えず・`createdAt` 昇順（原文の順序）のまま**入力へ含める。見出し行（「組み合わせNG:」等）も落とさない。

```js
"表現レギュレーション（原文・記載順。見出しと配下項目の関係を読み取ること）:",
rules.map((r) => `- ${r.description || r.pattern}`).join("\n")
```

あわせて配色の渡し方を変える。役割別のHEX（main/sub/accent/background）ではなく、**重複を除いた色リスト**を「使ってよい色の境界」として渡す。

```js
"ブランドカラー（この範囲で構成する）: #041024 / #2460F0 / #FFFFFF"
```

### C. ライターの責務にコントラスト確保を追加（`config/prompts/banner-image-prompt-writer.md`）

システムプロンプトへ以下を追加する。

- 配色はブランドカラーの範囲で構成し、**どの面にどの文字色を載せるかを散文へ明記する**
- 文字と背景のコントラストを必ず確保する。低コントラストの組み合わせを書かない
- レギュレーション原文は記載順に読み、見出し（「組み合わせOK:」「組み合わせNG:」「推奨比率:」など）と配下項目の関係を尊重する。**NG側に列挙された配色・表現は採用しない**

### D. 画像プロンプトの配色ブロックを色リストへ（`src/core/openai-image.js`）

散文アセンブリ（`assembleWrittenBannerImagePrompt`）の確定配色ブロックを、役割別HEXから色リストへ変更する。具体的な使い方はライターの散文が担うため、決定論ブロックは境界の明示だけでよい。

```
変更前: 確定配色: main=#FFFFFF(見出し・本文) / sub=... / accent=... / background=...
変更後: ブランドカラー（この3色で構成する）: #041024 / #2460F0 / #FFFFFF
        文字と背景のコントラストを必ず確保する。palette外の色を主要色に使わない。
```

レギュレーション原文は画像プロンプトへは入れない（ライターの散文に反映済みのため。トークン増を避ける）。

**フォールバック経路（`writtenImagePrompt` が空）は現行のJSONダンプ組み立てのまま**変更しない。後方互換を維持する。

## 4. 不変条件

| 契約 | 扱い |
|---|---|
| `colorDecision` / `promptJson.colorScheme` のデータ構造 | 不変 |
| `assertBannerImageColorContract`（一致検証） | 不変 |
| `applyRegulationRules`（NG語の置換） | 不変（`pattern` を持つルールのために維持） |
| `extractPaletteFromText` の役割推定ロジック | **Phase 1では不変**（削除はPhase 2） |
| copyBriefロック・OCR/ロゴ検証・テンプレ構造契約 | 不変 |
| フォールバック経路のプロンプト組み立て | 不変 |

## 5. 実装ステップ

1. **NG判定の修正**（A）＋テスト。`Orange` を含む行が specified に入り、`組み合わせNG:` が ng に入ることを固定する
2. **ライターへの受け渡し**（B）＋テスト。`expressionRules` が原文順で入力に含まれること、色リストが重複排除されることを検証
3. **システムプロンプト更新**（C）
4. **画像プロンプトの配色ブロック**（D）＋テスト。散文アセンブリが色リスト形式であること、フォールバック経路が不変であることを検証
5. **E2E検証**（§6）

各ステップでテストを通してから次へ進む。

## 6. 検証・受け入れ基準

1. `npm test` 全グリーン（既存497件を壊さない）
2. 新規テスト:
   - `Orange` を含むルールが specifiedRules に分類される
   - `組み合わせNG:` `禁止` `avoid` は従来どおり ngRules に分類される
   - ライター入力にレギュレーション全文が原文順で含まれる
   - ライター入力・画像プロンプトの色リストが重複排除されている
   - 散文アセンブリの配色ブロックに役割別HEX表記が無い
   - フォールバック経路のプロンプトが従来と完全一致
3. **実案件でのE2E比較**（cmo-ai-lite案件、問題が出たテンプレ）:
   - 青地に濃色文字が発生しないこと
   - 配色比率（White・Cloud Gray 55〜65%）が反映され、白基調になること
   - NG項目（グラデーション多用・#FF6B3D主役・#088C84全面背景）が採用されないこと
4. ライター失敗時にフォールバックで完走すること

## 7. 対象外（Phase 2以降）

- `extractPaletteFromText` の役割推定ロジック（ROLE_PATTERNS・距離40字・単色フォールバック）の削除
- Stage 1・Stage 2 への渡し方の変更（今回はNG判定の修正のみ）
- レギュレーション取り込み時にMarkdown階層を保持する仕組み
- 既存60枚の再生成（画像は生成時のパレットで焼き付いているため、運用判断）

## 8. リスクと軽減策

| リスク | 軽減策 |
|---|---|
| 配色の振れ幅が広がる（案ごとに主役色が変わる） | レギュレーションに日本語で「背景は必ず#041024」と書けば伝わる。パーサではなくAIが読むため書き方の自由度は上がる |
| ライターが可読性を守らない | システムプロンプトで明示（C）。§6-3のE2Eで確認。守れない場合はPhase 2でコントラスト検証を追加 |
| ライター入力トークン増 | **実測 1,330字 ≒ 1,197トークン、$0.006/枚**（ライター現状$0.078に対し約8%増）。件数が多い案件では上限設定を検討するが、現状27件では不要 |
| **A の修正でNGリスト項目1件が指示側へ移る** | 「成果保証や煽りコピーにOrange/Redを使う。」は本来NGリスト配下の項目で、誤爆により偶然NG判定されていた。修正後は指示側へ移る。ただし**NGリスト5項目のうち4項目（#088C84全面背景・#FF6B3D主役・赤黄金黒・グラデーション多用）は現状すでに指示側にあり**、状況は本質的に変わらない。ライター（B）へは原文順で渡るため文脈から正しく解釈される。Stage 1・Stage 2 の文脈喪失はPhase 2で対処する |
| `組み合わせNG:` 見出し自体の判定 | 引き続きNG判定される（単語境界マッチに合致） |
| 既存60枚は再生成しないと直らない | 事実として明示。運用判断に委ねる |
